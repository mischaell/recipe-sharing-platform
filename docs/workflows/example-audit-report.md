# Consistency audit — example dynamic-workflow run

> Generated by the `/recipe-audit` dynamic workflow: 3 read-only `Explore`
> subagents fanned out across feature areas in parallel, then synthesized.
> This is example output — findings reflect the code at the time of the run and
> are a starting point, not a verified bug list.

## Top fixes

1. **`LikeButton` doesn't roll back optimistic state on error** — a failed
   like/unlike leaves the button showing the wrong state. *(Shared components)*
2. **Recipe edit silently drops ingredient/step write failures** — the title can
   save while related rows don't, corrupting the recipe. *(Recipes)*
3. **Signup & reset-password forms surface no errors** — unlike login, they don't
   use `useActionState`, so failures are invisible to the user. *(Auth)*

## Auth area

- `app/signup/page.tsx` — No error state handling; signup doesn't use
  `useActionState` like login does → add `useActionState` to display
  `state?.error`.
- `app/reset-password/page.tsx` — Never displays action result (error or
  success) → wrap the form in `useActionState` to show feedback.
- `app/lib/auth/get-user.ts` — `getUser()` returns `null` on *any* error, so
  routes can't tell "not logged in" from "fetch failed" → distinguish auth
  failure from system error for guard logic.
- `app/login/page.tsx` — No server-side guard redirecting already-authenticated
  users → add an early `getUser()` check that redirects to `/dashboard`.
- `middleware.ts` — Redirect rule sends authenticated users away from `/`; the
  home page should stay public → exclude `/` from the redirect condition.
- `app/lib/auth/actions.ts` — Error-message shapes diverge (`resetPassword`
  includes an env-var hint others don't) → standardize the error shape.

## Recipes area

Ownership checks are **solid and consistent** — create, edit, and delete all
verify the logged-in user and recipe ownership before writing; view is correctly
public. Remaining items are error-handling:

- `app/recipes/[id]/edit/actions.ts` — Ingredient/step delete+insert failures are
  logged but not surfaced; a partial save can corrupt a recipe → return an error
  (or warning) instead of completing silently. **(highest priority)**
- `app/recipes/new/actions.ts` — User-facing error leaks DB detail ("check the
  database schema") → return a generic, actionable message.
- `app/recipes/[id]/edit/actions.ts` — `updateRecipe` returns a bare
  `error.message` with no fallback, unlike `createRecipe` → add a fallback
  message for consistency.
- `app/recipes/[id]/actions.ts` — `deleteComment` returns "Comment not found" for
  any fetch failure, masking RLS/authorization errors → log the real error and
  return a specific message.

## Shared components area

- `app/components/LikeButton.tsx` — Optimistic state isn't reverted when the
  server action fails → snapshot and restore `isLiked`/`likeCount` on error.
  **(highest priority)**
- `app/components/LikeButton.tsx` — `router.refresh()` runs even on failure →
  move it into the success branches only.
- `app/components/CommentItem.tsx` — On delete failure `isDeleting` stays set, so
  the button is stuck disabled with no retry → clear the state on error.
- `app/components/CommentForm.tsx` — Errors are only shown inline; easy to miss →
  ensure failures reliably reach the user (e.g. a toast).
- `RecipeCard`, `RecipeList`, `CommentsSection` — Clean (presentation/filtering
  only, no client-side mutations).

## Cross-cutting themes

- **Inconsistent error *shape*** across server actions (bare message vs. message
  + fallback vs. message + env hint). Worth a single shared error helper.
- **Errors that never reach the user** — swallowed on the client (LikeButton,
  CommentForm) or never wired to a UI surface (signup, reset-password).
- **Silent partial failures** — the highest-risk pattern: edit-recipe and the
  like button both let the UI/DB drift out of sync when a sub-operation fails.
